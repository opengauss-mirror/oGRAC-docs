# oGRAC引擎多写技术特性概述

## 1. 多写能力概述

oGRAC引擎采用存算分离架构，通过分布式缓存、事务MVCC机制和多主集群高可用技术实现透明多读多写能力。分布式透明集群(DTC, Distributed Transparent Cluster)是支撑这一能力的核心架构，它由多个关键组件协同工作，确保多节点并发读写时的数据一致性和事务隔离性。

透明多写能力的主要特性包括：

- 全节点支持读写，无主从区分
- 跨节点事务一致性保证
- 分布式MVCC实现
- 集群 `SCN` 推进与可见性同步机制
- 分布式锁管理
- 高可用和故障自动恢复

oGRAC引擎通过 `DRC`、`DCS`、`DLS`、`MES` 等分布式组件实现集群化功能。

## 2. DMS 相关组件概述

分布式内存服务（`DMS`，Distributed Memory Service）是多写共享集群服务的跨实例内存协调部分，主要通过 `DRC`、`DCS`、`DLS` 和 `MES` 支持以下功能。`DMS` 不作为独立数据库进程部署，不提供持久化存储，也不会把各实例的本地 `Buffer Pool` 合并为可直接寻址的全局内存。

### 2.1 跨节点MVCC实现

MVCC (Multi-Version Concurrency Control) 机制在分布式环境下需要特殊处理，以确保跨节点的数据一致性。

**核心特性：**

- 支持跨实例CR页面构建
- 通过事务快照、远端事务状态和集群 `SCN` 推进确保版本可见性一致

**实现细节：**

- 事务标识与实例信息共同用于跨实例识别事务
- 数据修改生成新版本，并记录在undo日志中
- 跨节点查询时，通过CR页面构建可见数据视图

### 2.2 跨节点 `SCN` 推进

`SCN`（System Change Number）是由秒、微秒和序列字段组成的 64 位时间序列值，用于建立集群内的时间和可见性边界。跨节点 `SCN` 推进机制使各实例能够在事务访问、页面传输和恢复过程中使用不落后的 `SCN`，并通过消息传播逐步收敛；`SCN` 本身不是独立的全局提交序号，事务可见性仍需结合事务状态、快照和 `Undo`/`CR` 页面判断。

**实现原理：**

- 通过广播机制实现节点SCN同步
- 采用自旋锁控制SCN更新的原子性
- 当本地SCN小于其他节点广播的SCN时，自动更新本地SCN
- 为跨实例事务可见性提供一致的推进边界

### 2.3 分布式锁

分布式锁服务(DLS, Distributed Lock Service)负责管理跨节点的锁资源，确保并发操作的数据一致性。

**实现机制：**

- 通过MES消息传递机制跨节点传递锁请求
- 支持自旋锁等锁操作原语
- 实现分布式锁等待和超时机制
- 支持锁降级；跨实例死锁由集群监控与检测流程识别并处理

### 2.4 分布式缓存服务(DCS)

分布式缓存服务(DCS, Distributed Cache Service)是透明多写架构中负责管理跨节点页面缓存、页面所有权和CR页面构建的关键组件。

#### 2.4.1 DCS核心概念

**页面所有权：**

- 页面目录会标记一个当前拥有者（`Owner`），同时可以保留多个共享（`S`）副本
- 拥有者的页面锁模式可以是共享（`S`）或排他（`X`）；只有持有 `X` 权限时才能修改页面
- 其他实例可以持有共享锁（`S`）并读取页面；申请 `X` 权限时需要使不再适用的共享副本失效

**EDP机制：**

- EDP(Earlier Dirty Page)表示节点上存在比当前页面版本更早的脏页
- 用于追踪和管理分布式环境下的页面版本依赖关系
- 确保页面刷新和检查点操作的正确性

**CR页面构建：**

- CR(Consistent Read)页面是为满足MVCC一致性读要求而构建的历史版本页面
- 支持堆表(HEAP)和索引(BTREE)的CR页面构建
- 通过分布式消息机制在节点间请求和传输CR页面

#### 2.4.2 DCS消息结构

不同 DCS 消息携带的字段并不相同。页面请求和所有权转移类消息可携带页面标识、请求模式、当前模式、请求版本等字段，消息公共头提供来源等通用信息；页面传输消息还会携带页面的 `LSN`、`SCN`、脏页/`EDP` 状态和页面内容。`CR` 请求、`EDP` 通知等消息只携带完成各自操作所需的字段。接收方会根据具体消息中的请求版本以及页面 `LSN`/`SCN` 进行必要的版本校验，过期请求在资源迁移期间暂停或拒绝，避免旧消息覆盖新状态。

#### 2.4.3 DCS核心功能

**1. 页面请求与所有权管理**

DCS 实现页面请求和所有权转让机制：

- **本地优先**：先检查请求实例本地 `Buffer Pool` 中是否存在满足锁模式和可见性要求的页面
- **请求页面流程**：本地没有可用页面时，请求者向该页面所属资源分区的 `DRC Master` 查询状态，再向当前 `Page Owner` 请求页面数据；`DRC Master` 是资源分区级角色，不是固定的业务主节点
- **所有权转让**：当页面所有者收到请求后，通常直接将缓存页面传输给请求方并更新锁状态；只有集群缓存中没有可用副本时，才由请求实例通过 `DSS` 装载页面
- **写权限转换**：请求 `X` 权限时使其他实例的只读副本失效；脏页转移前必要时先刷新保护该页面的 `Redo`，旧副本按需登记为 `EDP`
- **批量操作**：支持批量页面请求和所有权声明，提高系统吞吐量

**2. 脏页管理与EDP清理**

DCS提供了完善的脏页管理机制：

- **脏页追踪**：通过EDP位图跟踪节点上的脏页状态
- **脏页清理**：检查点由数据库存储引擎将符合条件的脏页写入共享数据文件，DCS 负责维护转移过程中的副本和 `EDP` 状态
- **目录协调**：由页面所属资源分区的 `DRC Master` 协调页面状态，不存在统一固定的页面主节点

**3. CR页面构建与一致性读**

为支持分布式MVCC，DCS实现了跨节点的CR页面构建：

- **CR请求处理**：可处理不同类型的CR请求
- **目录查询**：查询页面所属资源分区的 `DRC Master`，确定 `CR` 构建所需的页面和事务信息
- **CR页面构造**：在持有原始页面的节点上构造CR页面，并传输给请求节点

#### 2.4.4 DCS通信机制

DCS采用可靠的消息通信机制，确保节点间数据传输的正确性：

**消息重试机制：**

- 通过MES消息传递机制实现消息可靠发送
- 按预设的重试间隔和等待超时处理发送失败；目标节点仍存活时可以持续重试，周期性重试计数用于输出告警，不等同于固定的重试上限
- 检测目标节点状态，避免向不可用节点发送消息

**超时控制：**

- 设置单条消息等待超时，防止单次等待长时间阻塞；该超时不等同于整个页面或事务请求的总等待时间
- 对 `CR` 请求设置单独的超时控制，并结合请求类型处理整体等待

**状态同步：**

- 根据 `CMS` 发布的集群视图更新节点状态和消息路由
- 通过消息重试、超时控制和目标节点状态检查处理节点不可访问场景

#### 2.4.5 DCS性能优化

DCS实现了多种性能优化策略：

- **批量操作**：支持批量页面请求、批量所有权声明和批量释放操作
- **本地优先**：优先使用本地缓存，减少网络通信
- **并发处理**：支持多线程并发处理DCS消息
- **异步操作**：部分操作支持异步执行，提高响应速度

#### 2.4.6 DCS异常处理

DCS具备异常处理机制，并与集群 `Reform` 协同完成资源清理：

- **资源清理**：节点故障时配合 `Reform` 清理相关页面状态、资源和锁
- **异常清理**：节点状态变化时清理失效的页面、锁和消息上下文
- **日志记录**：详细记录异常情况，便于问题诊断

DCS作为透明多写架构的核心组件，通过分布式缓存管理维护多节点环境下的页面一致性和访问协作，为oGRAC引擎的透明多读多写能力提供支撑。

### 2.5 分布式资源目录(DRC)

分布式资源目录(DRC, Distributed Resource Catalog)是透明多写架构中负责管理集群范围内资源分配、资源所有权和资源迁移的核心组件。DRC用于维护多节点环境下的资源目录和一致性管理。

#### 2.5.1 DRC核心概念

- **资源分区管理**：DRC将系统资源划分为多个分区(part)，每个分区由特定节点管理，实现资源的分布式管理
- **资源所有权**：每个资源(如页面、锁)有明确的所有权标识，控制资源的访问权限
- **EDP机制**：(Earlier Dirty Page)，用于跟踪和管理脏页状态，确保数据一致性
- **资源迁移**：在集群Reform过程中，实现资源所有权的平滑迁移
- **资源回收**：自动回收失效或超时的资源，提高系统稳定性

#### 2.5.2 核心数据结构

DRC 目录按资源分区组织，目录项记录资源标识、分区管理节点、当前所有者、锁模式、共享副本和脏页依赖等状态，并使用迁移版本区分不同轮次的 `Reform`。页面目录项与非页面锁目录项使用不同的状态字段，但都由分区管理节点统一仲裁。

#### 2.5.3 核心功能实现

1. **资源所有权管理**：根据锁请求和当前持有者状态授予、转移或回收资源权限。

2. **资源分区管理**：按分区分散目录管理压力，在 `Remaster` 时迁移分区及其目录状态。

3. **页面脏副本管理**：记录 `EDP` 依赖，配合检查点和页面所有权转移清理旧版本。

4. **DRC资源集中模式**

DRC 支持资源集中模式（`DRC_IN_REFORMER_MODE`）。当业务仅运行在 `Reformer` 节点上时，可以通过开启此模式减少跨节点资源请求：

- 资源目录集中在 `Reformer` 节点
- 通过修改参数 `DRC_IN_REFORMER_MODE` 控制；该参数为重启生效，修改后需要重启实例
- 适用于读写负载集中在特定节点的场景

#### 2.5.4 与Reform的协作

DRC与集群Reform机制紧密协作，在节点加入或离开集群时实现资源的平滑迁移：

### 2.6 集群Reform机制

集群 `Reform` 是透明多写架构中保证高可用性的关键机制，用于处理节点加入、离开、故障等场景，确保集群配置的一致性。`Reform` 期间可能暂时限制部分访问，实际影响取决于成员变化类型、恢复阶段和集群状态。

#### 2.6.1 Reform核心概念

- **Reformer节点**：由 `CMS` 集群视图选定、负责协调本轮 `Reform` 的实例；它不等同于某个页面的 `Page Owner` 或资源分区的 `DRC Master`
- **Reform角色**：节点在Reform过程中扮演的角色，包括 `STAY`、`JOIN`、`LEAVE`、`ABORT` 和 `FAIL`
- **Reform模式**：`Reform` 的触发方式，主要分为计划内和计划外两类
- **资源重分配**：在Reform过程中重新分配系统资源所有权
- **部分恢复**：在节点加入或恢复时，只恢复必要的数据和状态
- **集群视图**：记录当前集群节点状态、版本和稳定性信息的数据结构

#### 2.6.2 Reform状态和流程

Reform的主要流程包括：

1. **准备阶段**：确定参与Reform的节点和各自角色
2. **构建通信通道**：确保节点间通信正常
3. **资源重分配(Remaster)**：重新分配资源所有权
4. **必要时执行恢复**：处理故障实例的日志、事务和页面状态，使集群重新达到一致
5. **关闭临时通道**：清理Reform过程中的临时资源
6. **开放服务**：允许客户端连接和请求

#### 2.6.3 Reform过程详细实现

##### 2.6.3.1 Reform触发机制

当 `CMS` 发布的集群视图发生变化时，数据库实例根据成员状态和当前工作状态判断是否需要进入 `Reform`。需要重构时，先确定参与节点及其角色，再进入准备阶段；如果仅收到不改变成员状态和资源归属的心跳或状态上报，则更新本地集群视图并继续提供服务。

##### 2.6.3.2 Reform状态机

Reform实现了复杂的状态机来管理Reform过程中的状态转换，状态机定义如下：

状态机基于四个维度的状态组合来确定下一步操作：

- 前CMS状态：节点在CMS中的之前的状态(ONLINE/OFFLINE)
- 后CMS状态：节点在CMS中的目标状态
- 前工作状态：节点的之前的工作状态(JOINING/JOINED/LEAVING/LEFT)
- 后工作状态：节点的目标工作状态

根据这些状态组合，状态机会决定：

- 需要执行的操作列表（包括 `REFORM_LIST_BEFORE`、`REFORM_LIST_AFTER`、`REFORM_LIST_JOIN`、`REFORM_LIST_LEAVE`、`REFORM_LIST_ABORT` 和 `REFORM_LIST_FAIL`）
- 是否为成员变更操作
- 是否为不可能的状态转换(用于错误检测)

##### 2.6.3.3 Reformer 节点流程

`Reformer` 节点的具体职责包括：

- 构建和维护Reform通信通道
- 协调资源重分配过程
- 收集和同步所有节点的状态
- 处理异常情况和错误恢复
- 通知所有节点Reform完成

##### 2.6.3.4 其他参与节点流程

其他参与节点在 `Reform` 过程中的主要职责是响应 `Reformer` 的协调并执行相应操作，包括报告状态、建立临时通信通道、导出或导入资源、处理分配到本节点的恢复任务，并在完成后返回确认信息。

##### 2.6.3.5 集群视图管理

集群视图记录成员状态、工作状态、版本和稳定性信息，是资源分配和消息路由的共同依据。`CMS` 发布新视图后，各实例校验视图版本并同步本地状态；使用旧视图的请求会被暂停或拒绝，避免在资源迁移期间继续使用过期目录。

##### 2.6.3.6 Reform完成检查

只有当通信通道、资源重分配、必要的日志与事务恢复以及节点状态确认均完成后，`Reform` 才会退出。完成检查通过后，实例更新本地集群视图并重新开放受影响的读写请求；若任一阶段超时或失败，则进入重试或异常终止流程。

#### 2.6.4 Reform模式和类型

Reform支持多种Reform模式和类型，以适应不同的场景：

1. **Reform模式**：
   - 计划内 `Reform`：如正常的节点加入或退出，核心是成员视图同步和资源目录迁移
   - 计划外 `Reform`：如节点故障，除资源重分配外，还需要处理故障实例的 `Redo`、`Undo` 和未提交事务
   - 无 `Reform` 状态

2. **节点角色**：
   - `REFORM_ROLE_STAY`：保持在集群中的节点
   - `REFORM_ROLE_JOIN`：新加入集群的节点
   - `REFORM_ROLE_LEAVE`：离开集群的节点
   - `REFORM_ROLE_ABORT`：异常终止的节点
   - `REFORM_ROLE_FAIL`：上一次加入或离开过程失败的节点

3. **CMS状态**：
   - `RC_CMS_ONLINE`：节点在线
   - `RC_CMS_OFFLINE`：节点离线

4. **工作状态**：
   - `RC_JOINING`：节点正在加入集群
   - `RC_JOINED`：节点已加入集群
   - `RC_LEAVING`：节点正在离开集群
   - `RC_LEFT`：节点已离开集群

#### 2.6.5 异常处理和容错

Reform机制设计了完善的异常处理和容错机制：

1. **状态修复**：可修复可能的状态不一致问题

2. **超时处理**：通过带超时的锁操作限制长时间等待，并辅助发现死锁或异常状态

3. **失败重试**：关键阶段在限定次数和超时时间内重试，超过阈值后进入异常处理

4. **位图同步**：可确保节点状态位图的一致性

5. **错误检测和恢复**：通过错误码和状态检查进行异常处理

#### 2.6.6 与DRC的协作

Reform与DRC紧密协作，实现资源的平滑迁移和重分配：

在Reform过程中，Reform和DRC的协作流程如下：

1. Reform触发资源重分配(Remaster)过程
2. DRC协调各节点准备重分配
3. `Reformer` 根据新的集群视图计算资源分配方案
4. 各节点执行资源迁移
5. 迁移完成后确认并通知Reform
6. Reform继续后续的Reform步骤

#### 2.6.7 Remaster过程详细实现

Remaster过程是Reform机制中的核心环节，负责在节点角色或集群拓扑变化时重新分配和迁移资源。下面详细介绍Remaster的实现机制：

##### 2.6.7.1 Remaster核心管理结构

`Remaster` 以资源分区为基本单位，维护每个分区的管理节点、导出节点、导入节点和迁移版本。页面资源和非页面锁资源分别生成迁移任务，任务完成后由新的分区管理节点接管目录。

##### 2.6.7.2 Remaster过程的四个阶段

1. **准备阶段(REMASTER_PREPARE)**
   - 初始化Remaster管理器
   - 清理离开节点的资源
   - 等待所有节点准备就绪

2. **任务分配阶段(REMASTER_ASSIGN_TASK)**
   - `Reformer` 根据新的集群拓扑和资源分区分配任务
   - 确定每个分区的导出节点和导入节点

3. **资源迁移阶段(REMASTER_MIGRATE)**
   - 执行缓冲区资源迁移
   - 执行锁资源迁移
   - 等待迁移完成

4. **清理和完成阶段**
   - 释放迁移后的资源
   - 确认所有任务完成
   - 更新集群状态

##### 2.6.7.3 Remaster完成条件

所有导出和导入任务完成、离开节点的资源已清理、新管理节点已确认目录版本，并且各节点对迁移结果达成一致后，`Remaster` 才能向后续 `Reform` 阶段推进。

#### 2.6.8 日志回放流程详细实现

日志回放流程用于在 `Reform` 需要接管故障实例时恢复数据一致性，主要适用于计划外故障等需要重放故障实例日志的场景。下面介绍日志回放的主要阶段：

##### 2.6.8.1 日志回放核心流程

1. **日志读取阶段**
   - 并行读取多个节点的redo日志
   - 加载日志批次到内存缓冲区

2. **日志分析阶段(ANALYSIS)**
   - 分析日志批次，确定需要恢复的页面
   - 构建恢复数据集

3. **日志回放阶段(RECOVERY)**
   - 并行回放日志组
   - 应用变更到数据页面

4. **一致性验证阶段**
   - 验证数据一致性
   - 更新SCN和恢复点

#### 2.6.9 Reform性能监控

oGRAC 提供了丰富的Reform性能监控指标，便于跟踪和分析Reform过程：

- 准备阶段耗时
- 恢复阶段耗时
- 资源迁移耗时

### 2.7 DTC 多写协作路径

`DTC`（Distributed Transparent Cluster）是数据库实例内承接多写协作的执行层。一次跨实例页面访问通常遵循“本地优先、目录定位、所有权协商、必要时访问共享存储”的路径：

1. 请求实例先检查本地 `Buffer Pool`，确认页面版本和锁模式满足访问要求。
2. 本地没有可用页面时，向页面所属资源分区的 `DRC Master` 查询目录状态，再向当前 `Page Owner` 请求页面或所有权；`DRC Master` 是资源分区级角色，不是固定的业务主节点。
3. 请求 `X` 权限时，DCS 使其他实例的只读副本失效。页面所有权转移前，必要时先刷新保护该页面的 `Redo`，旧的脏页依赖按 `EDP` 记录。
4. 只有集群缓存中不存在可用副本时，才从 `DSS` 装载页面。`DSS` 负责共享文件和块设备访问，不负责页面锁、所有权或事务可见性。
5. 检查点由存储引擎组织脏页写回；对于由其他实例持有的脏页，DTC/DCS 通知当前 `Page Owner` 处理后再推进检查点位置。

事务与 DDL 在同一协作边界内完成一致性控制：DTC 通过集群消息查询远端事务状态并推进本地 `SCN`，一致性读按事务状态、快照和 `Undo`/`CR` 页面判断可见性；逻辑 DDL 提交后同步到存活实例，远端刷新或失效字典缓存。节点故障时，`Reform` 依据新的集群视图重分配资源，并处理故障实例的 `Redo`、`Undo` 和未提交事务。

上述路径体现了几个边界：`DMS` 不是全局可寻址内存池，`DRC Master` 不等于页面所有者，`Reformer` 不等于业务主节点，`DSS` 也不替代 DTC/DMS 的一致性控制。理解这些边界有助于正确分析页面访问延迟、锁等待、检查点推进和故障恢复行为。

## 3. DSS介绍

### 3.1 DSS核心功能

分布式存储服务（`DSS`，Distributed Storage Service）为数据库实例提供统一的共享文件和块设备访问能力，为透明多写架构提供持久化存储基础。

**核心功能：**

- 统一的文件操作API抽象
- 分布式存储访问能力
- 多节点数据共享

**职责边界：**

- 提供文件创建、打开、读写、删除、重命名以及异步 I/O 等统一能力
- 屏蔽底层共享存储介质的访问差异
- 不负责页面所有权、分布式锁、事务可见性或缓存副本失效，这些由 `DTC`/`DMS` 协同完成
- 具体部署形态和底层存储实现不改变上述职责边界
